# Research: Which pi credentials survive a six-hour unattended window? (wayfinder ticket #3)

Ticket: ilteoood/paseo-pi-actions#3. Map context: ilteoood/paseo-pi-actions#1 (GitHub-hosted runners, one manual `workflow_dispatch` per window, public repo, daemon identity restored from repo secrets, fresh session per window, nothing secret persisted).

Environment inspected: pi `@earendil-works/pi-coding-agent` **1.4.0** installed at
`/Users/ilteoood/.local/share/fnm/node-versions/v24.17.0/installation/lib/node_modules/@earendil-works/pi-coding-agent/`.
No secret values are reproduced below; provider names and JSON shapes only.

## Summary

Only two credential shapes survive a 6-hour unattended window without human action: (a) a static API key from the environment, which never refreshes and therefore never changes, and (b) an OAuth credential whose stored **access** token is still valid for the whole window — pi only refreshes when <5 minutes of validity remain. The moment pi *does* refresh, it persists the rotated credential into `auth.json` inside the job, and that write is discarded when the job ends; for providers that invalidate the old refresh token (Anthropic and xAI demonstrably do), the copy held in a repo secret is then dead. The provider actually configured here is `opencode-zen` (an OAuth provider supplied by the third-party `npm:opencode-zen-oauth` extension, not a pi built-in), and Zen's rotation semantics are not publicly documented, so that arrangement cannot be relied on for repeated jobs. Recommend a static API-key credential (or Anthropic workload-identity federation, which pi supports) so the job has no rotating secret at all, with `pi auth check --provider <p> --json --no-refresh` as the preflight and `PI_CODING_AGENT_DIR` pointed at `$RUNNER_TEMP`.

## Findings

### 1. Which credential types run unattended for 6 hours

1. **Claim (direct evidence):** API keys from environment variables are the CI-intended mechanism and need no refresh. pi documents `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `OPENCODE_API_KEY`, `OPENROUTER_API_KEY`, `GEMINI_API_KEY`, etc. as process-environment credentials, and says "Environment variables are useful in CI and anywhere Pi should not store the key."
   **Sources:** installed `docs/providers.md` §"Use an API key from the environment" (table); `docs/environment-variables.md` §"Pi Process Configuration" (last paragraph). **Support:** direct evidence. **Confidence:** high.

2. **Claim (direct evidence):** An API-key credential can also be resolved from a command without writing the key to disk (`"key": "!security find-generic-password ..."`), and a stored credential may carry an `env` object whose values outrank the process environment for that provider. Useful when the workflow wants the key to come from the runner's secret store rather than a plain env var; note pi caches the command output for the process lifetime and an empty/failed command leaves the key unresolved until restart.
   **Sources:** installed `docs/providers.md` §"Load an API key from a command" and §"Provider Specific Config" (`env` object). **Support:** direct evidence. **Confidence:** high.

3. **Claim (direct evidence — refresh semantics):** For OAuth credentials pi refreshes only when the token has less than five minutes of validity left, re-checks that condition under a credential-store lock, and **persists the refreshed credential to `auth.json` before releasing the lock**. The code comment states the hazard explicitly: "Once a refresh starts, the provider may already have rotated the refresh token, so the refresh and its persistence ignore `signal` and are bounded only by a timeout. Otherwise a cancelled caller could discard the only valid refresh token."
   **Sources:** `packages/ai/src/auth/resolve.ts` (`DEFAULT_OAUTH_MINIMUM_VALIDITY_MS = 5 * 60 * 1000`, `refreshStoredOAuthCredential`); `packages/ai/src/models.ts` (`resolveRefreshCredential` comment: "A refresh that has started survives cancellation or a superseding model refresh, so a rotated refresh token is always persisted"); `packages/coding-agent/src/core/auth-storage.ts` (`AuthStorage.modify` writes merged JSON back to `auth.json`, file created with mode `0o600`). **Support:** direct evidence. **Confidence:** high.

4. **Claim (direct evidence — consequence for CI):** Therefore, inside a 6-hour job: if the credential materialised at job start still has ≥5 minutes of access-token validity, no refresh happens and nothing rotates; if it expires mid-window, pi refreshes, writes the rotated pair into the job-local `auth.json`, and that write is lost when the runner is destroyed. A repo secret holding the pre-rotation refresh token is reusable afterwards **only if the authorization server does not invalidate the old refresh token**.
   **Sources:** findings 3 + the pi CLI's own storage choice (see finding 7). **Support:** interpretation of direct evidence. **Confidence:** high.

5. **Claim (direct evidence — rotation does invalidate copies for some providers):** For Anthropic's Claude subscription OAuth, the refresh grant is single-use: "a successful refresh rotates the pair and invalidates the old refresh token"; a pi extension bug that refreshed without persisting produced `invalid_grant / "Refresh token not found or invalid"` and required a manual `/login`. For xAI the same pattern is documented as revoking the old token (`"Refresh token has been revoked"`).
   **Sources:** anthropics/claude-code issue #80585 (body: "Anthropic's refresh grant appears to be single-use (it rotates the refresh token)"), Sarrius/pi-multi-account issue #22 (body: "Anthropic rotates the refresh token on every refresh call … the refresh token stored in `auth.json` is already revoked server-side"), anomalyco/opencode issue #37059 (body: "xAI rotates refresh tokens. Process A refreshes successfully and invalidates the old token"). **Support:** direct evidence (vendor-adjacent bug reports; not vendor documentation). **Confidence:** medium-high for Anthropic/xAI; the general pattern should be assumed for any rotating provider until proven otherwise.

6. **Claim (direct evidence — the provider in use):** The local agent dir has exactly one model-provider credential: provider key `opencode-zen`, `type: "oauth"`, with the OAuth field shape `{refresh, access, expires, orgID, allowedModels[]}`. `mcp-auth.json` holds one MCP-server credential, key `mcp__slack|https://mcp.slack.com/mcp`, shape `{serverUrl, discovery{...}, oauthState, tokens{access_token, token_type, expires_in, scope, refresh_token}, tokensExpireAt}` (no values reproduced). No API-key provider is configured locally; `settings.json` declares the package `npm:opencode-zen-oauth`, whose manifest registers the provider id `opencode-zen` (name "OpenCode Zen") with both an `oauth` method (device-flow login + `refreshZenToken`) and an `apiKey` method that resolves `OPENCODE_API_KEY`.
   **Sources:** `/Users/ilteoood/.pi/agent/auth.json` (keys only), `/Users/ilteoood/.pi/agent/mcp-auth.json` (keys only), `/Users/ilteoood/.pi/agent/settings.json` (`packages[]`), `opencode-zen-oauth@1.2.11` `src/extension.ts` (`createProvider({ id: "opencode-zen", … })`). **Support:** direct evidence. **Confidence:** high.

7. **Claim (direct evidence — Zen refresh mechanics):** Zen's refresh is a device-token refresh: `POST https://opencode.ai/console/auth/device/token` with `{grant_type:"refresh_token", refresh_token, client_id:"opencode-cli"}`, and the client always stores the `refresh_token` returned in that response in place of the old one (`credentialFrom(poll)` → `refresh: poll.refresh_token`). OpenCode's own equivalent handler does the same (`refresh: token.refresh_token`), and its account tests assert the stored `refresh_token` is replaced by the new one after a refresh.
   **Sources:** `opencode-zen-oauth@1.2.11` `src/auth.ts` (`credentialFrom`, `refreshZenToken`); anomalyco/opencode `packages/core/src/plugin/provider/opencode.ts` (refresh handler); anomalyco/opencode commit `00d6841` (#20558) test "token refreshes before expiry when inside the eager refresh window" (mock returns `refresh_token: "rt_new"`, row asserts `rt_new` persisted). **Support:** direct evidence. **Confidence:** high (the response always carries a refresh token and clients overwrite the stored one).

8. **Claim (researcher inference, unverified):** Whether the Zen console **invalidates** the previous refresh token when it issues a new one is not documented anywhere I could find (no OpenCode docs page, changelog, or issue states it). Because the response shape is rotation-shaped and because rotation-with-invalidation is the observed norm for Anthropic and xAI, treating a repo-secret copy of a Zen refresh token as reusable across jobs is unsafe. **Sources:** absence of documentation on opencode.ai console docs; the two vendor-adjacent rotation reports above. **Support:** researcher inference. **Confidence:** low-medium — flag as the single most important unverified point.

9. **Claim (researcher inference, low confidence):** The Zen access token appears to be long-lived rather than hours-long. The OAuth credential's stored `expires` (epoch ms) in the local `auth.json` is ~13.7 days after the Slack MCP credential's `tokensExpireAt`; if both credentials were written around the same time, Zen's `expires_in` is on the order of 1.2 million seconds (~14 days). The Slack MCP entry's own `expires_in` is 43200 s (12 h), which by itself outlives a 6-hour window. Neither figure is documented by OpenCode. **Sources:** local `auth.json` / `mcp-auth.json` numeric fields (no token values); opencode commit `00d6841` uses `expires_in: 60` in a mock only. **Support:** researcher inference from timestamps. **Confidence:** low — do not plan around it.

10. **Claim (direct evidence — practical precedent):** A third-party pi CI runner documents exactly the two options this ticket is weighing and labels the OAuth one as needing maintenance: "Option A: API key (recommended) — static, never expires"; "Option B: pi auth.json — uses your local pi OAuth session. May need periodic rotation."
    **Sources:** `butttons/pi-action-runner` README. **Support:** direct evidence (third-party, not authoritative). **Confidence:** medium.

### 2. What `pi auth check --provider <p> --json` reports, and its exit codes

11. **Claim (direct evidence — CLI contract):** `pi auth check` prints `ready`, `not_ready`, or `invalid` and exits `0`, `1`, or `2` respectively; `--json` writes the structured result; `--credentials` emits the resolved credential; `--no-refresh` disables the refresh that is otherwise the default. Credential-printing commands write secrets to stdout.
    **Sources:** installed `docs/cli.md` §"Credential commands"; `packages/coding-agent/src/main.ts` `runAuthCommand` (`process.exitCode = result.status === "ready" ? 0 : result.status === "not_ready" ? 1 : 2`). **Support:** direct evidence. **Confidence:** high.

12. **Claim (direct evidence — exact JSON):** The JSON object is `AuthCheckResult` serialized, optionally plus `credentials`:
    - `{"status":"ready","provider":"<p>","authType":"api_key"|"oauth"}` (exit 0)
    - `{"status":"not_ready","provider":"<p>","reason":"provider_not_found"|"credentials_not_configured"|"credential_not_available"}` (exit 1)
    - `{"status":"invalid","provider":"<p>","reason":"invalid_state"}` (exit 2)
    `--credentials` adds `"credentials":"<secret>"` only when status is `ready`. Bad arguments / unknown flags print an error on stderr and set exit 2 for `check` (exit 1 for the print commands).
    **Sources:** `packages/coding-agent/src/cli/auth-check.ts` (`AuthCheckStatus`, `AuthCheckReason`, `AuthCheckResult`, `checkProviderAuth`); `packages/coding-agent/src/cli/auth-command.ts` (`getAuthCredential`); `packages/coding-agent/src/main.ts` (`JSON.stringify({...result, ...(credential ? {credentials: credential} : {})})`); `packages/coding-agent/test/auth-check.test.ts` (expected objects). **Support:** direct evidence. **Confidence:** high.

13. **Claim (direct evidence — what "ready" means depends on the flag):**
    - Default (refreshing): `checkProviderAuth` calls `modelRuntime.checkAuth` and then `modelRuntime.getAuth`, i.e. it resolves real request auth and **refreshes and persists** an OAuth credential that is within 5 minutes of expiry. A failed refresh throws `ModelsError` and is reported as `{"status":"invalid",…,"reason":"invalid_state"}` (exit 2).
    - `--no-refresh`: uses `ReadOnlyAuthStorage` (never creates `auth.json` or its parent directory) and skips `getAuth`. `checkAuth` for a stored OAuth credential returns `{source:"OAuth", type:"oauth"}` **without looking at `expires`**, so `ready` there means "a credential is present", not "it is currently usable".
    - An unresolved environment reference in a stored key (`"key": "$MISSING"`) counts as `not_ready`/`credentials_not_configured`.
    **Sources:** `packages/coding-agent/src/main.ts` (`command.noRefresh ? new ReadOnlyAuthStorage() : AuthStorage.create()`), `packages/coding-agent/src/cli/auth-check.ts`, `packages/ai/src/models.ts` (`checkProviderAuth` implementation), `packages/coding-agent/src/core/auth-storage.ts` (`ReadOnlyAuthStorage`), `packages/coding-agent/test/auth-check.test.ts` ("does not create an auth file or its parent directory", "does not treat an unresolved stored environment reference as configured"). **Support:** direct evidence. **Confidence:** high.

14. **Claim (researcher inference, needs a 30-second local check):** `pi auth check --provider opencode-zen …` will report `{"status":"not_ready","provider":"opencode-zen","reason":"provider_not_found"}` even with valid credentials, because `opencode-zen` is registered by an **extension**, and the auth-command path runs before any extension is loaded. Evidence chain: (i) in `main.ts`, `runAuthCommand(args)` is invoked immediately after the `extensionFactories` array is merely assembled and before `handlePackageCommand`, `handleConfigCommand`, `parseArgs`, and the `createRuntime` factory that passes `extensionFactories` into `createAgentSessionServices`; (ii) `createAuthCheckModelRuntime` builds its runtime with only `{credentials, modelsStore, allowNetwork:false, refreshOnCreate:false}` — no extension factories, no resource loader — so only built-in providers plus `models.json` providers exist; (iii) `checkAuth` returns `undefined` when `this.providers.get(providerId)` misses, which maps to `provider_not_found`; (iv) `/Users/ilteoood/.pi/agent/models.json` does not exist, so no config-form provider covers the id; (v) `custom-provider.md` only promises that factory-registered providers are available to "startup model selection and `pi --list-models`", not to the auth commands. **Verification to run locally:** `pi auth check --provider opencode-zen --json; echo $?`. **Support:** researcher inference from source reading (not executed). **Confidence:** medium-high.

### 3. Relocating `auth.json` so nothing secret can be cached or uploaded

15. **Claim (direct evidence):** `auth.json` lives in the agent directory (`<agent-dir>/auth.json`), whose location is set by `PI_CODING_AGENT_DIR` (default `~/.pi/agent`). Sessions live under the same agent directory and can be relocated with `PI_CODING_AGENT_SESSION_DIR` or `--session-dir`.
    **Sources:** installed `docs/configuration.md` §"Agent directory"; installed `docs/environment-variables.md` §"Pi Process Configuration" (`PI_CODING_AGENT_DIR`, `PI_CODING_AGENT_SESSION_DIR`); `packages/coding-agent/src/core/auth-storage.ts` (`join(getAgentDir(), "auth.json")`). **Support:** direct evidence. **Confidence:** high.

16. **Claim (direct evidence — why the location matters in a public repo):** GitHub's own guidance: "We recommend that you don't store any sensitive information, such as access tokens or login credentials, in files in the cache path. Anyone with read access can create a pull request…"; and "Any run that can read a cache restores its contents as-is … never store secrets or other sensitive data in a cache. Untrusted workflows can read sensitive cache contents". Artifacts are likewise reachable by "anyone with read access to the repository", which for a public repo is everyone.
    **Sources:** GitHub docs "Dependency caching reference"; GitHub docs "Dependency caching" §"Cache security"; GitHub REST docs "List artifacts for a repository". **Support:** direct evidence (interpretation: public repo ⇒ read access ⇒ cache/artifact contents are not a secret store). **Confidence:** high.

17. **Claim (interpretation):** The concrete rule for this job: set `PI_CODING_AGENT_DIR="$RUNNER_TEMP/pi-agent"` (runner temp is outside the checkout and wiped with the runner), materialise `auth.json` there with mode `0600`, and never add that path to `actions/cache`, `upload-artifact`, or any step that `git add`s the workspace. Pointing `PI_CODING_AGENT_DIR` at `$GITHUB_WORKSPACE/.pi` would write the credential inside the checkout — the one place an artifact upload or a stray `git add -A` can capture it. Note also that `pi auth check` **without** `--no-refresh` creates `auth.json` (and its parent dir) if absent, so even a preflight can write the secret; use `--no-refresh` when the preflight must not mutate.
    **Sources:** findings 11–16. **Support:** researcher interpretation. **Confidence:** high.

18. **Claim (direct evidence — related project-trust caveat):** pi reads a project's `sessionDir` setting *before* resolving project trust, so a hostile/accidental project setting can redirect session storage even when trust is declined; sessions can contain prompts, tool output, and anything pasted into the conversation.
    **Sources:** installed `docs/security.md` §"Understand project trust" (the `sessionDir` exception); §"Reduce impact and improve recovery" (review sessions before sharing). **Support:** direct evidence. **Confidence:** high — relevant because the workflow runs `--approve` in an unattended job.

### 4. Anthropic workload-identity federation in GitHub Actions

19. **Claim (direct evidence — pi supports it):** With no key or token set, pi's `anthropic` provider uses WIF when `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID` and `ANTHROPIC_IDENTITY_TOKEN_FILE` are set; the Anthropic SDK exchanges the identity token for a short-lived access token and refreshes it itself, **re-reading the identity token file**, so the file must be kept fresh for long sessions. `ANTHROPIC_SERVICE_ACCOUNT_ID` and `ANTHROPIC_WORKSPACE_ID` are passed through when set.
    **Sources:** installed `docs/providers.md` §"Use an API key from the environment" (paragraph after the table); `packages/ai/src/providers/anthropic.ts` (`anthropicApiKeyAuth().resolve`: returns `{auth:{}, env: federation, source:"workload identity federation"}` only when all three required vars are non-empty; keys and `ANTHROPIC_AUTH_TOKEN`/`ANTHROPIC_OAUTH_TOKEN` win over it). **Support:** direct evidence. **Confidence:** high.

20. **Claim (direct evidence — what GitHub Actions requires):** Usable in GitHub Actions. Needs `permissions: id-token: write`; a federation **issuer** registered for `https://token.actions.githubusercontent.com` in discovery mode; a **service account** and a **federation rule** in the Claude Console (org admin required); the rule's `match` pins the workflow (`subject_prefix`, `audience`, plus claims such as `repository_owner`/`ref`); the job sets `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID` and (when the rule spans workspaces) `ANTHROPIC_WORKSPACE_ID`; the JWT is fetched from `ACTIONS_ID_TOKEN_REQUEST_URL` with `audience=https://api.anthropic.com` and written to the file named by `ANTHROPIC_IDENTITY_TOKEN_FILE`. The console returns a token starting `sk-ant-oat01-` with an `expires_in`.
    **Sources:** platform.claude.com "Use WIF with GitHub Actions" (prerequisites, workflow YAML, federation rule JSON, cURL exchange); anthropics/claude-agent-sdk-python `.github/actions/setup-claude-auth/action.yml` (composite action that mints the token via `core.getIDToken("https://api.anthropic.com")`, writes it to `$RUNNER_TEMP` mode 0600, and spawns a detached refresher). **Support:** direct evidence. **Confidence:** high.

21. **Claim (direct evidence — identity-token lifetime):** "Each GitHub-issued identity token expires roughly 5 minutes after issuance. The token-request endpoint (`ACTIONS_ID_TOKEN_REQUEST_URL`) stays valid for the entire job, so you can fetch a fresh token at any point." For jobs longer than the Anthropic token's lifetime the SDK re-reads the identity-token file on each refresh, so the fetch step must be repeated (or wrapped in a background loop). Anthropic's own action does this with a detached process because "a token minted here would expire before CLI invocations late in the job exchange it."
    **Sources:** platform.claude.com "Use WIF with GitHub Actions" §"Acquire and use a token"; claude-agent-sdk-python `setup-claude-auth/action.yml` comment. **Support:** direct evidence. **Confidence:** high. (Rule configuration can also set `token_lifetime_seconds`, e.g. `600` in the documented example.)

22. **Claim (direct evidence — subject-claim gotcha for a young public repo):** Repositories created after **July 15, 2026** use an immutable `sub` format that includes owner and repo IDs: `repo:OWNER@OWNER-ID/REPO@REPO-ID:ref:refs/heads/BRANCH`, instead of `repo:owner/repo:ref:refs/heads/branch`. A federation rule's `subject_prefix` must match the format the repository actually emits. Also, `pull_request` runs use `repo:owner/repo:pull_request`, so a rule scoped to `ref:refs/heads/<branch>` excludes them (good here: the map's trigger is `workflow_dispatch`).
    **Sources:** GitHub docs "OpenID Connect reference" §"Immutable subject claims" and §"Example subject claims"; platform.claude.com "Use WIF with GitHub Actions" §"Restrict which workflows can authenticate". **Support:** direct evidence; **researcher inference** that a `workflow_dispatch` run yields a `ref:refs/heads/<branch>`-shaped subject (GitHub's docs only enumerate environment, pull_request, branch, and tag examples — verify by decoding one real token in the run). **Confidence:** high for the immutable-format change; medium for the exact `workflow_dispatch` subject shape.

23. **Claim (direct evidence — preflight behaviour for WIF):** `pi auth check --provider anthropic --json` will report `ready` when the three WIF env vars are non-empty, because the anthropic provider's API-key `resolve()` returns an auth result for that case. It does **not** validate that the identity-token file exists, is fresh, or is accepted by Anthropic — so a `ready` WIF check is a configuration check, not a proof that the exchange will succeed. (pi does not require a `check()` implementation for this provider, so `checkAuth` falls back to `resolveProviderAuth`.)
    **Sources:** `packages/ai/src/providers/anthropic.ts` (resolve logic reads env values only); `packages/ai/src/models.ts` (`checkProviderAuth`: uses `apiKey.check` when present, otherwise `resolveProviderAuth`). **Support:** direct evidence + interpretation. **Confidence:** high.

### 5. Recommendation

24. **Claim (recommendation):** For a 6-hour unattended job whose daemon must keep working without a human:
    - **Preferred:** Anthropic over workload-identity federation. Nothing long-lived is stored, no refresh token exists to go stale, and the credential survives any window. Requires an Anthropic organization with Console admin (federation rule + service account), `id-token: write`, and a background refresher for the 5-minute identity token (as Anthropic's own action does). Billed to the Anthropic org's API account, not a Claude subscription. `pi auth check --provider anthropic --json` works because `anthropic` is a built-in provider.
    - **Simplest:** one static API key for a built-in provider as a repo secret (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, or Zen's `OPENCODE_API_KEY`). Never refreshes, so the preflight and the 6-hour window are both trivial. Caveat to verify in the OpenCode console: the `opencode-zen-oauth` README states the v2 console "hides API keys from workspace members", so a member account may not be able to mint a Zen API key at all.
    - **Only if the Zen OAuth credential must be used:** base64 the local `auth.json` into a repo secret, materialise it at `$RUNNER_TEMP/pi-agent/auth.json` (mode 0600) at job start, export `PI_CODING_AGENT_DIR="$RUNNER_TEMP/pi-agent"`, and accept that the secret can go stale: any refresh the job performs writes a rotated credential that dies with the runner. Mitigations: run the preflight with `--no-refresh` so the job never rotates before the daemon starts; expect to re-login locally and re-upload the secret after a failed job; do not plan around `pi auth check --provider opencode-zen` working at all (finding 14).
    **Sources:** findings 1–23. **Support:** researcher recommendation. **Confidence:** medium-high (the Zen-specific rotation question and the Zen API-key availability are the two open inputs).

25. **Claim (recommendation — preflight the workflow should run):**
    ```bash
    export PI_CODING_AGENT_DIR="$RUNNER_TEMP/pi-agent"   # outside the checkout; wiped with the runner
    mkdir -p "$PI_CODING_AGENT_DIR"
    # (OAuth variant only) materialise auth.json here from the secret, then: chmod 600 "$PI_CODING_AGENT_DIR/auth.json"

    # Read-only, never writes auth.json, never rotates:
    pi auth check --provider anthropic --json --no-refresh    # exit 0 ready / 1 not_ready / 2 invalid

    # End-to-end proof before the daemon starts (this is what actually catches a dead credential):
    pi --print --provider anthropic --model <model-id> "reply with ok"
    ```
    Use the refreshing form (`pi auth check --provider <p> --json`, no `--no-refresh`) when you deliberately want to prove the credential can refresh and exchange; exit 2 then means the refresh itself failed. Never pass `--credentials` in CI (it writes the secret to stdout), and never run `pi auth print-bearer-token` without redirecting its stdout.
    **Sources:** findings 11–14, 17; installed `docs/cli.md` §"Credential commands" ("Credential-printing commands write secrets to stdout"). **Support:** researcher recommendation grounded in direct evidence. **Confidence:** high for the mechanics; the provider/model in the two commands depends on the decision in finding 24.

## Contradictions

- **Feature intent vs shipped default:** the original request behind `pi auth check` asked for a command that checks "without refreshing credentials or mutating Pi state" (earendil-works/pi issue #7152), while the shipped default *does* refresh and can write `auth.json` (`docs/cli.md`: refresh is the default; `main.ts` uses the writable `AuthStorage.create()` unless `--no-refresh`). Not a behavioural contradiction — `--no-refresh` restores the requested behaviour — but the read-only guarantee is opt-in, which matters for a job that must not rotate a secret.
- **GitHub cache risk is being actively reduced:** GitHub shipped read-only cache tokens for untrusted triggers in June 2026, limiting cache poisoning from fork PRs; the "never put credentials in a cache" rule still stands. Recorded so the ticket does not overstate the cache threat.
- **`checkAuth` vs expiry:** "ready" from `--no-refresh` means the credential exists, while "ready" from the refreshing default means pi resolved usable auth. Two different meanings for the same word — this is a documentation-level gap, not conflicting sources.

## Missing evidence

- **Does the OpenCode Zen console invalidate the previous refresh token when it issues a new one?** No public documentation found. This is the single fact that decides whether a repo-secret Zen refresh token survives repeated jobs (finding 8).
- **Zen access-token lifetime (`expires_in`).** Not documented; only a low-confidence inference from local timestamps (finding 9). If it is genuinely ~14 days, a 6-hour window never refreshes, which would make the Zen OAuth arrangement viable in practice — but that is unproven.
- **Does `pi auth check` see extension-registered providers?** Source reading says no; not executed (finding 14). Needs a local `pi auth check --provider opencode-zen --json` run.
- **Can this account mint a Zen API key?** The extension README says workspace members cannot see API keys in the v2 console; whether this account is a member or an owner was not determined.
- **Does the Slack MCP credential rotate/invalidate?** Its `tokens` block has a `refresh_token` and `expires_in: 43200`; Slack-side rotation semantics were not researched. Relevant only if the job needs MCP tools.
- **Exact `sub` claim for a `workflow_dispatch` run of this repo** (legacy vs immutable format) — must be read off a real token before pinning the WIF federation rule.
- **`source_check` did not validate the rotation claim:** the tool returned "Status: unclear (confidence 0.30) — automated semantic support or contradiction assessment is unavailable". Validation therefore rests on the directly-read primary sources cited above, not on the checker.
