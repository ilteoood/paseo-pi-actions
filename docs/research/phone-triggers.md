# Research: verified ways to start a window from a phone (wayfinder ticket #5, ilteoood/paseo-pi-actions)

## Summary

The GitHub mobile **app** can run `workflow_dispatch` workflows — changelog-confirmed since July 2024 — even though the official GitHub Mobile docs page still does not mention Actions at all ("docs silent"). The **mobile web** UI exposes the same `Run workflow` dialog (write access, workflow file on the default branch), but a user report claims the button silently no-ops on the mobile site, and the docs never describe branch/input behaviour as mobile-specific. A **phone shortcut** (iOS Shortcuts / Android HTTP Shortcuts) hitting `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` with a repo-scoped fine-grained PAT (`Actions: write`) is the only phone surface that can pass inputs *and* target an arbitrary branch/tag without opening GitHub — at the cost of holding a live credential on the device. `repository_dispatch` is strictly worse for this use: it costs `Contents: write` (push-equivalent blast radius) and cannot target a non-default ref at all.

## Findings

### 1. Does the GitHub mobile app expose Actions / the ability to run a workflow?

1. **Claim: yes — the app can manually run `workflow_dispatch` workflows.** **Sources:** [Run workflows set as workflow_dispatch manually (changelog, 2024-07-30)](https://github.blog/changelog/2024-07-30-run-workflows-set-as-workflow_dispatch-manually/). **Support:** direct evidence — "Developers can now manually run workflows set with `workflow_dispatch` directly from the Workflow view (Repository -> Actions -> Workflows) on GitHub Mobile." **Confidence:** high.
2. **Claim: the app has had Actions *viewing/management* since Oct 2022.** **Sources:** [Introducing Actions on GitHub Mobile (changelog, 2022-10-04)](https://github.blog/changelog/2022-10-04-introducing-actions-on-github-mobile/). **Support:** direct evidence — view a workflow-run, its jobs and logs; "re-running single jobs, failed jobs as well as entire workflows"; cancellation of running checks. **Confidence:** high.
3. **Claim: the July 2024 "What's New in Mobile" roundup names "Workflow Dispatching" as one of three headline features, and locates it in "the list of workflow runs for a given workflow".** **Sources:** [What's New in Mobile, July Update (2024-08-07)](https://github.blog/changelog/2024-08-07-whats-new-in-mobile-july-update/). **Support:** direct evidence — "Workflow Dispatching! Kick off new Actions on the go from the list of workflow runs for a given workfl[ow]". **Confidence:** high. (This is the only wording about *where* the action lives; it does not say whether inputs or a branch can be chosen — see Missing evidence.)
4. **Claim: docs are silent — the official GitHub Mobile docs page lists the app's capabilities and does not mention Actions, workflows, or workflow dispatch anywhere.** **Sources:** [GitHub Mobile (docs.github.com)](https://docs.github.com/en/get-started/using-github/github-mobile). **Support:** direct evidence — the verbatim capability list is: manage/triage/clear notifications; read, review and collaborate on issues and pull requests; edit files in pull requests; search for, browse and interact with users, repositories and organizations; push notification on mention; search code in a repository; 2FA; verify sign-ins; Copilot Chat. No Actions entry. **Confidence:** high (for "docs silent").
5. **Claim: the app's own feature lists are also silent, and are not evidence of absence.** **Sources:** [GitHub on the App Store](https://apps.apple.com/us/app/github/id1477376905) (listing shows v1.282.0, capability bullets: notifications, issues/PRs, review+merge, labels/assignees/projects, browse files and code, discover repos); [GitHub on Google Play](https://play.google.com/store/apps/details?hl=en_US&id=com.github.android) (same bullets; "What's new" mentions "In-progress workflow steps now show a live elapsed timer"). **Support:** direct evidence of the listings' contents; **researcher inference** that the store bullets are marketing copy that lags the changelog — the Google Play "What's new" entry is the only store text that touches workflows, and it implies workflow runs are rendered in-app. **Confidence:** medium (the inference).
6. **Claim: the app can also edit workflow files (so a `workflow_dispatch` trigger can be added from the phone).** **Sources:** [Edit workflow files on GitHub Mobile (changelog, 2023-05-11)](https://github.blog/changelog/2023-05-11-edit-workflow-files-on-github-mobile/). **Support:** interpretation — the changelog snippet states you can modify workflow files and create/merge PRs from the app. **Confidence:** medium (snippet-level, not re-fetched in full).

### 2. Mobile web "Run workflow": requirements and limits

7. **Claim: the documented requirements for the web UI are: the workflow must declare `workflow_dispatch`; the workflow file must exist on the default branch; and the user needs write access to the repository.** **Sources:** [Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow); [Events that trigger workflows — `workflow_dispatch`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). **Support:** direct evidence — "To trigger the `workflow_dispatch` event, your workflow must be in the default branch." / "Write access to the repository is required to perform these steps." / "This event will only trigger a workflow run if the workflow file exists on the default branch. … On the GitHub UI, the 'Run workflow' button will be present if the workflow file exists on the default branch." **Confidence:** high. No token is involved — the browser session carries the identity (researcher inference from the absence of any token requirement in the docs).
8. **Claim: the web dialog does support choosing a branch and filling inputs.** **Sources:** [Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) — "Select the **Branch** dropdown menu and click a branch to run the workflow on." / "If the workflow requires input, fill in the fields."; [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) — "Once a workflow has run at least once, you can dispatch it against any branch or tag via the GitHub API or GitHub CLI." **Support:** direct evidence, but note the two pages are not perfectly aligned: the how-to says the UI has a branch dropdown, while the events reference names only the **API/CLI** for dispatching against *any* branch or tag. **Confidence:** high for the existence of the dropdown; medium for "any branch/tag from the UI". **Researcher inference:** the dropdown is the same "Use workflow from" selector reported by community members, and it appears on a *specific workflow's* page, not on the "All workflows" list ([community discussion #169535](https://github.com/orgs/community/discussions/169535)).
9. **Claim: input limits — up to 25 top-level `inputs`, max 65,535 characters of payload.** **Sources:** [Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow); [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). **Support:** direct evidence. **Confidence:** high.
10. **Claim: what mobile web cannot do — it cannot show/run a workflow whose file is not on the default branch (the button is absent), and there is a live user report that on the mobile site the button appears but does nothing.** **Sources:** [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows); [community discussion #172839 "Mobile website: 'Run workflow' button does not start workflow"](https://github.com/orgs/community/discussions/172839). **Support:** direct evidence for the default-branch rule. For the bug report, direct evidence of the report's text (extracted from the page's own metadata/HTML): "Open a repository with Actions enabled on the GitHub **mobile site**. Go to the **Actions** tab. Open a workflow and click the 'Run workflow' dropdown. Press the green Run workflow button." … "Actual behavior: The button switches to 'Running workflow…' but nothing happens. Refreshing the page shows that **no workflow was started**. This only happens on the **mobile web UI**. On desktop, it works normally." (Device: Pixel 9 Pro, Firefox.) **Confidence:** medium — this is a single unreplied user report on a feedback discussion, not a GitHub statement; it may be browser- or date-specific. It is also the only evidence found that the mobile site renders the button at all.
11. **Claim: the docs never describe mobile-web-specific Actions behaviour.** **Sources:** [Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) — the procedure is written for "GitHub" web UI with no mobile variant; [GitHub Mobile (docs.github.com)](https://docs.github.com/en/get-started/using-github/github-mobile) — no Actions entry. **Support:** direct evidence of absence. **Confidence:** high for "docs silent"; **researcher inference** that mobile web therefore behaves like the responsive desktop UI.
12. **Claim: iOS Universal Links push GitHub links into the app, so a mobile-web bookmark may not stay in the browser.** **Sources:** [GitHub Mobile (docs.github.com) — "Managing Universal Links for GitHub Mobile on iOS"](https://docs.github.com/en/get-started/using-github/github-mobile). **Support:** direct evidence — Universal Links are enabled automatically; tapping a GitHub link opens GitHub Mobile unless you long-press → "Open". **Confidence:** high.

### 3. Calling the dispatch API from a phone shortcut

13. **Claim: endpoint A is `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches`, body `ref` (required, branch **or tag** name) + `inputs` (optional, max 25).** **Sources:** [REST API endpoints for workflows](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event). **Support:** direct evidence — "You can replace workflow_id with the workflow file name"; "`ref` (string) (required) The git reference for the workflow. The reference can be a branch or tag name."; "`inputs` (object) Input keys and values configured in the workflow file. The maximum number of properties is 25." Response is `workflow_run_id`, `run_url`, `html_url`. Classic PATs need `repo` scope. **Confidence:** high.
14. **Claim: endpoint A needs the fine-grained permission **Actions: write** (repository permission), scoped to the target repository.** **Sources:** [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens) — row `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` | `write` | PAT, under section `## Repository permissions for "Actions"`. **Support:** direct evidence (row fetched from the page; independently re-read under the "Actions" heading via a page-local query). **Confidence:** high.
15. **Claim: endpoint B is `POST /repos/{owner}/{repo}/dispatches` (`repository_dispatch`), body `event_type` (required, ≤100 chars) + `client_payload` (≤10 top-level properties, <64 KB).** **Sources:** [REST API endpoints for repositories — Create a repository dispatch event](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event). **Support:** direct evidence. **Confidence:** high.
16. **Claim: endpoint B needs the fine-grained permission **Contents: write**.** **Sources:** [Permissions required for fine-grained personal access tokens](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens) — row `POST /repos/{owner}/{repo}/dispatches` | `write` | PAT, under section `## Repository permissions for "Contents"`. **Support:** direct evidence. **Confidence:** high. Corroboration: the `peter-evans/repository-dispatch` action's maintainer and users state `contents: write` is what's needed ([issue #165](https://github.com/peter-evans/repository-dispatch/issues/165)) — secondary, same conclusion.
17. **Claim: `repository_dispatch` cannot target a non-default ref, and also requires the workflow file on the default branch.** **Sources:** [Events that trigger workflows — `repository_dispatch`](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). **Support:** direct evidence — `GITHUB_REF` = "Default branch"; "This event will only trigger a workflow run if the workflow file exists on the default branch." **Confidence:** high. This is the key structural reason `workflow_dispatch` (which takes `ref`) beats it for a phone trigger.
18. **Claim: iOS Shortcuts can send the request itself — the `Get Contents of URL` action supports method and request body, and headers are editable.** **Sources:** [Request your first API in Shortcuts on iPhone or iPad](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios) (Apple documents `Get Contents of URL` as the way to call an API); [Save This One iOS Shortcuts setup](https://savethisone.com/integrations/ios-shortcuts) — "Find the Get Contents of URL action … Under Headers, replace the `Authorization` value with: `Bearer YOUR_API_TOKEN`"; [httpbot.io](https://httpbot.io/automate-api-calls-apple-shortcuts/) — "set the HTTP method, add headers, and pass a request body". **Support:** direct evidence for the action's role (Apple); **interpretation** for the Headers field, which Apple's own guide page does not spell out in the text fetched — the header capability is documented by third parties, not by Apple. **Confidence:** medium-high (widely used, but the "Headers" UI is not confirmed on an Apple-owned page here).
19. **Claim: Android has a no-server equivalent: HTTP Shortcuts (open source) supports arbitrary methods incl. POST, custom request headers, and Bearer authentication.** **Sources:** [HTTP Shortcuts documentation — Features/Technical](https://http-shortcuts.rmy.ch/). **Support:** direct evidence — "Supports HTTP and HTTPS … and methods GET, POST, PUT, DELETE, PATCH, HEAD, OPTIONS and TRACE"; "Basic Authentication, Digest Authentication, Bearer Authentication and Client Certificate Authentication"; "Custom request headers"; "Custom request body"; plus home-screen shortcuts/widgets and variable injection. **Confidence:** high (vendor docs).
20. **Claim: the request must carry a valid `User-Agent` header — GitHub rejects requests without one (403 for an invalid one).** **Sources:** [Getting started with the REST API — `User-Agent`](https://docs.github.com/en/rest/using-the-rest-api/getting-started-with-the-rest-api). **Support:** direct evidence — "All API requests must include a valid `User-Agent` header." / "Requests with no `User-Agent` header will be rejected. If you provide an invalid `User-Agent` header, you will receive a `403 Forbidden` response." **Confidence:** high for the requirement; **unconfirmed** whether Shortcuts/HTTP Shortcuts send an acceptable UA by default (the iOS client is URLSession-based and normally sends one, but I found no primary source stating it — verify on the device).
21. **Claim: no server is required — both apps run the HTTP request on-device.** **Sources:** [HTTP Shortcuts documentation](https://http-shortcuts.rmy.ch/) (shortcut/widget triggers the request directly); [Apple Shortcuts User Guide](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios) ("When the shortcut is run, this action makes the API request"). **Support:** direct evidence. **Confidence:** high.

### 4. Is a token stored on a phone dangerous, and what limits the blast radius?

22. **Claim: GitHub's own framing is that a PAT is password-equivalent, and it recommends a more secure method first, plus an expiry.** **Sources:** [Managing your personal access tokens — "Keeping your personal access tokens secure"](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). **Support:** direct evidence — "Personal access tokens are like passwords, and they share the same inherent security risks."; "we highly recommend adding an expiration"; "GitHub automatically removes personal access tokens that haven't been used in a year" (classic). **Confidence:** high.
23. **Claim: fine-grained PATs are the radius-limiting option — one resource owner, optionally only selected repositories, and explicit per-permission grants; classic PATs are the opposite.** **Sources:** [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). **Support:** direct evidence — "Each token is limited to access resources owned by a single user or organization."; "Each token can be further limited to only access specific repositories for that user or organization."; "Each token is granted specific, fine-grained permissions"; the creation flow says "Under **Repository access**, select which repositories you want the token to access. You should choose the minimal repository access that meets your needs."; by contrast "Your personal access token (classic) can access every repository that you can access."; also: "There is a limit of 50 fine-grained personal access tokens you can create." **Confidence:** high.
24. **Claim: a fine-grained PAT limited to one repo with only `Actions: write` cannot push code — but it can still start runs of that repo's existing workflows.** **Sources:** permission mapping above ([permissions page](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens)) plus the push endpoints requiring `Contents: write`. **Support:** **researcher inference** — the permissions page lists `Contents`/`Workflows` write as separate permissions, so `Actions: write` alone does not grant `PUT /repos/{owner}/{repo}/contents/{path}`. **Confidence:** medium-high. The residual risk is not "attacker edits my code" but "attacker repeatedly dispatches a workflow that already exists" — for this project that means repeatedly booting a pi window (minutes spend, daemon pairing, relay exposure). **Researcher inference.**
25. **Claim: on iOS the token lives inside the shortcut itself, which is iCloud-synced, shareable, and only "stored locally in an encrypted format" in Apple's words.** **Sources:** [Secure features in the Shortcuts app (Apple Platform Security guide)](https://support.apple.com/guide/security/secure-features-in-the-shortcuts-app-secec043bdae/web). **Support:** direct evidence — "In the Shortcuts app, shortcuts are optionally synced across Apple devices using iCloud. Shortcuts can also be shared with other users through iCloud. Shortcuts are stored locally in an encrypted format." **Confidence:** high for the statement; **researcher inference** that a token pasted into a shortcut is therefore readable by anyone who opens the shortcut in edit mode and travels with iCloud sync/backups (corroborated by practitioner accounts: [Thingelstad, "Using API Credentials in Shortcuts"](https://www.thingelstad.com/2020/04/21/using-api-credentials.html) — most shortcuts "use a Text variable and put the token in that variable. This works, but it exposes problems if you share that Shortcut"). Apple documents **no** Keychain-backed secret store for Shortcuts. **Confidence:** medium (no primary Apple statement that tokens are plaintext; the absence of a secure-storage action is the evidence).
26. **Claim: rotation is the practical control, because revocation is manual.** **Sources:** [Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens) (expiration recommendation, 50-token limit, org approval policy) and [Token expiration and revocation](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/token-expiration-and-revocation). **Support:** interpretation. **Confidence:** medium. Practical implication for this project: a short-expiry token (docs default 30 days when pre-filled via URL parameters) means re-pasting a secret into the shortcut on a schedule — the hidden friction cost of this option.

### 5. Ranked recommendation (lowest friction first)

27. **1 — GitHub mobile app → repository → Actions → workflow → Run workflow.** Requirements: write access, workflow file on the default branch, app installed and signed in. Token: none. Cannot: no documented way to pass inputs or choose a non-default ref (see Missing evidence), and it is absent from the docs' feature list. **Tradeoff:** zero secret management and zero setup, at the cost of no per-window parameters — for this project's "one `workflow_dispatch` per window" constraint that is acceptable only if the window needs no inputs. **Sources:** [changelog 2024-07-30](https://github.blog/changelog/2024-07-30-run-workflows-set-as-workflow_dispatch-manually/), [docs.github.com GitHub Mobile](https://docs.github.com/en/get-started/using-github/github-mobile). **Confidence:** high for "it can dispatch"; low for the input/ref limitation (unverified either way).
28. **2 — Mobile browser (Safari/Chrome) → Actions → workflow → Run workflow.** Requirements: same write access, same default-branch rule, no token. Can pass inputs and pick a branch from the workflow page's dropdown. **Tradeoff:** the only UI path with inputs, but a live report says the button no-ops on the mobile web UI, and on iOS Universal Links may hijack the navigation into the app. **Sources:** [docs how-to](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow), [discussion #172839](https://github.com/orgs/community/discussions/172839), [Universal Links](https://docs.github.com/en/get-started/using-github/github-mobile). **Confidence:** medium (single unconfirmed bug report).
29. **3 — iOS Shortcut / Android HTTP Shortcuts → `POST /repos/{owner}/{repo}/actions/workflows/{workflow_id}/dispatches` with a fine-grained PAT (`Actions: write`, one repo, short expiry).** Requirements: the PAT, plus a valid `User-Agent` header. Can pass inputs *and* an explicit `ref` (branch or tag) — the only phone surface that can dispatch against a non-default ref. **Tradeoff:** a live credential on the device and a re-paste chore at expiry; one tap once built. **Sources:** [workflows endpoint](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event), [permissions page](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), [HTTP Shortcuts](https://http-shortcuts.rmy.ch/), [Apple Shortcuts API guide](https://support.apple.com/guide/shortcuts/request-your-first-api-apd58d46713f/ios). **Confidence:** high for the API mechanics; medium for the shortcut UI details.
30. **4 — `repository_dispatch` from a phone-adjacent surface.** Requires `Contents: write` (push-equivalent), runs only on the default branch, and adds a required `event_type` for a free-form `client_payload`. **Tradeoff:** strictly dominated by #3 for this use case: same phone plumbing, bigger token, less control over ref. Its only edge is arbitrary `event_type` filtering, which the project does not need. **Sources:** [repos endpoint](https://docs.github.com/en/rest/repos/repos#create-a-repository-dispatch-event), [permissions page](https://docs.github.com/en/rest/authentication/permissions-required-for-fine-grained-personal-access-tokens), [events reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows). **Confidence:** high.
31. **5 — Slack / chat button.** Slack's inbound webhooks start Slack workflows; going the other way (Slack → GitHub HTTP POST with an `Authorization` header) requires either Slack's outbound web-request step or a third-party automation (Zapier/Make/n8n) that holds the token for you. **Tradeoff:** moves the secret off the phone (good) but adds a third-party account, a paid plan, and an indirection layer (bad); I could not confirm the current availability of Slack's outbound web-request step from an authoritative Slack page. **Sources:** [Slack: workflow that starts outside of Slack](https://slack.com/help/articles/360041352714-Build-a-workflow--Create-a-workflow-that-starts-outside-of-Slack) (inbound direction only); secondary/conflicting: [zoelog](https://zoelog.vercel.app/projects/slack-workflow-automations/private-dms-from-a-slack-workflow) claims Slack removed the "send a web request" step, [larksuite](https://www.larksuite.com/en_us/blog/slack-workflow-builder) describes it as existing. **Confidence:** low.

## Contradictions

- **Can the UI dispatch against a non-default branch?** [Manually running a workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow) instructs "Select the **Branch** dropdown menu and click a branch to run the workflow on", while [Events that trigger workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows) says only "via the GitHub API or GitHub CLI" for dispatching against *any* branch or tag. Community reports say the branch selector exists but only on a specific workflow's page, not on the "All workflows" list ([discussion #169535](https://github.com/orgs/community/discussions/169535)). Not resolved here; it does not change the recommendation, because the API path is unambiguous.
- **Can the API dispatch a workflow whose file is NOT on the default branch?** A docs-repo review comment claims "workflow_dispatch is absolutely able to be triggered when the workflow file is not in the default branch. The issue lies in HOW it can be triggered: when it is in the default branch, the Github UI can be used. When it is not, then the Github UI cannot be used." ([github/docs commit de2cbf0](https://github.com/github/docs/commit/de2cbf0b7afa424e88723ab0122d51beb6ef15a7)). Current official docs say flatly "This event will only trigger a workflow run if the workflow file exists on the default branch" ([events reference](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)), and third parties restate that the API is subject to the same registration rule ([latchkey.dev](https://latchkey.dev/learn/github-actions/github-actions-workflow-dispatch-not-on-default-branch) — low-authority). Treat the API claim as unresolved.
- **Does the mobile web button work?** No GitHub statement either way; only the unreplied report above. Docs are silent on mobile web.
- **Slack outbound web-request step:** sources disagree on whether it still exists (see finding 31).

## Missing evidence

- **No primary source states whether the GitHub mobile app lets you choose a branch/ref or fill `workflow_dispatch` inputs.** The changelog only says "manually run workflows set with `workflow_dispatch` directly from the Workflow view"; the July 2024 roundup says "from the list of workflow runs for a given workflow". Nothing on inputs or ref selection. Must be verified on the device (that is prototype-ticket territory, and the ticket explicitly defers tap counts there).
- **No Apple-owned page confirms the `Headers` field of `Get Contents of URL`** (only third-party docs do), and no source confirms whether iOS Shortcuts sends a `User-Agent` that GitHub accepts.
- **No primary source on whether iOS Shortcuts has any Keychain-backed secret storage.** Apple's Shortcuts security page describes iCloud sync/sharing and local encryption only; there is no Apple statement that a token typed into a shortcut is or is not plaintext in the editor.
- **No authoritative Slack page confirming or denying the current outbound "send a web request" step.**
- **I could not run `gh issue view`** (no shell tool in this session); both issues were read from their public web pages instead — [issue #5](https://github.com/ilteoood/paseo-pi-actions/issues/5) and [issue #1](https://github.com/ilteoood/paseo-pi-actions/issues/1). Content matched the ticket's summary of the prior research.
- **App version dates:** the iOS listing showed v1.282.0 and the Google Play listing "Updated on Oct 22, 2026", read on 2026-10-23. App UI can change without a changelog entry, so any app-path claim is version-sensitive.
- **`source_check` was not used** for the permission-mapping and changelog claims; instead each was verified by fetching the primary page and reading the exact row/sentence (and, for the permission rows, by re-reading them under their section headings via a page-local query). Two independent reads agreed on both rows.
